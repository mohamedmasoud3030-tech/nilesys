# ADR-0011: Repository tooling stays on npm; Nx + pnpm is not adopted now

- **Status:** Accepted
- **Date:** 2026-10-19
- **Decided by:** the LENA integration agent, under the owner's delegation of technical decisions on
  2026-10-19 ("make the technical decisions, without creating new repositories"). Resolves **D-H**
  (`PRODUCT_PLAN.md` §10, task F0-10).
- **Supersedes:** only the *Monorepo/workspace* bullet of [ADR-0001](0001-technology-stack.md). Everything
  else in ADR-0001 stands: TypeScript strict, NestJS/Fastify, Next.js for web apps, PostgreSQL, modular
  monolith, and the binding constraints 1–6.

## Context

ADR-0001 chose Nx + pnpm for machine-enforced module boundaries. The repository was never moved to it:

- every merged and candidate branch uses npm with `package-lock.json` v3 (`npm ci`, `npm run typecheck`,
  `npm test`); `AGENTS.md`, `docs/agent-system/ARENA_SANDBOX.md` and the CI draft assume npm;
- all verification evidence (237/237 on real PostgreSQL 17 at `0207c13`) was produced with npm;
- `ARCHITECTURE.md` §3 lists the Nx/pnpm clause as an open ADR-vs-code gap;
- an untracked `pnpm-lock.yaml` appeared in one sandbox. It has `lockfileVersion: '9.0'` and one importer
  (`.`) that mirrors this `package.json`, so it was generated by a `pnpm install` run in that sandbox. No
  script, document or CI step uses it, and it has never been committed on any branch.

## Decision

1. **npm is the package manager.** `package-lock.json` is the only lockfile. Never run `pnpm install` or
   `corepack pnpm` in this repository.
2. **Nx is not adopted now.** When the first web app is created (`apps/web` or `apps/marketing`, see
   [ADR-0012](0012-nile-sites-live-in-nilesys.md)), the root becomes an **npm workspaces** project.
3. **ADR-0001 constraint 4 still binds** (boundaries enforced in CI). Until Nx exists, enforcement is a
   plain import-boundary check run by CI: `apps → engines → platform/shared`, with no reverse imports. It is
   added together with the CI workflow (task F0-3). Until then it is a documented rule only. This ADR does
   not claim that enforcement exists today.
4. **`pnpm-lock.yaml` is ignored, not deleted.** It is added to `.gitignore` so it cannot be committed by
   accident. Any copy on disk is left in place, because the owner's rules forbid deleting files on an
   agent's own initiative.

## Alternatives rejected

- **Move to Nx + pnpm now.** This changes the toolchain of every branch before the integration branch is
  merged. It invalidates the recorded evidence and the CI draft, and it gives no product feature.
- **Commit `pnpm-lock.yaml` beside `package-lock.json`.** Two lockfiles drift and let installs disagree.

## Consequences

- Positive: one toolchain matches all existing evidence, docs and the CI draft. Agents have one command set.
- Negative: no Nx project graph. Boundary checks must be scripted (decision 3).
- Reversibility: high. A later ADR may adopt Nx + pnpm once at least two apps exist and CI is green.

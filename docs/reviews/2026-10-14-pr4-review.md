## 3. Remaining risks (none blocks the merge)

1. **Test gap.** The committed tests cover 5 of the 8 locked paths. `change-email`, `delete-user` and
   `revoke-session` are verified only by scratch tests (rows 5–6). Recommendation: add them to §6b in a
   follow-up.
2. **Row locks become unavailable** on the five tables for the runtime role (row 9). Future refund,
   payment or shift code must serialise with advisory locks (row 10) or with unique constraints, not
   `SELECT … FOR UPDATE`.
3. **`cash_movements.status` (`pending → posted`) can no longer be updated** by the runtime. Resolving
   pending cash must append a row. The same applies to a sale's `void` status: voids become compensating
   return transactions. Both are handled in proposal 0007.
4. **New ledger tables are not protected automatically** (row 11). Each migration that adds one must
   include its own REVOKE and a privilege test.
5. **`list-sessions` reveals other demo visitors' raw session tokens.** They are unusable today: the
   cookie needs the HMAC signature, Bearer is not enabled, and `revoke-session` is locked (row 5). They
   would become exploitable if a bearer-token plugin were added.
6. Purging these tables (the daily demo reset) must run as the owner role. No reset job exists yet.
7. Pre-existing and not introduced here: gate finding G-7 (an unawaited `SET ROLE` in `engines/db/open.ts`)
   showed up again as a pg "query while already executing" deprecation warning during row 8.

## 4. Effects on future payments, refunds, locking and the cash drawer

| Area | Effect |
| --- | --- |
| Payments | No effect on current code (no payment code exists). New payment tables need their own REVOKE (risk 4) |
| Refunds | Must be compensating rows; serialise concurrent refunds with advisory locks (risks 2–3) |
| Transaction locking | `FOR UPDATE` / `FOR SHARE` on the five tables fails for `nile_app` (verified) |
| Cash drawer | The pending → posted transition must be an appended resolution row, not an UPDATE |

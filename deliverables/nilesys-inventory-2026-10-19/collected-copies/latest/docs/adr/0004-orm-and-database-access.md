# ADR-0004: ORM and database access

- **Status:** Accepted
- **Date:** 2026-09-04
- **Decided by:** Mohamed (product owner), with ChatGPT (strategist) and Arena (implementation)
- **Supersedes:** n/a

## Context

The stack (ADR-0001) is TypeScript-first with PostgreSQL. The persistence
layer must support a multi-tenant, tenant-isolated data model (ADR-0002) with
machine-enforceable safety, and must not obstruct the future complex SQL that
accounting/reporting will require.

## Decision

Adopt **Drizzle ORM + Drizzle Kit** for PostgreSQL access and migrations.

### Rationale

- Keep the persistence layer **TypeScript-native and close to SQL**.
- Prefer **transparent, inspectable SQL** over a heavier ORM abstraction.
- Use **Drizzle Kit to generate reviewable SQL migrations**.
- Keep **schema definitions modular and colocated** with the modules that own
  them where practical.
- Use **PostgreSQL capabilities directly** when they materially improve
  correctness, including constraints, indexes, transactions, and Row-Level
  Security (RLS). Drizzle supports native PostgreSQL RLS (roles and policies),
  so tenant isolation does not rely solely on application-layer discipline.
- Preserve **straightforward access to complex SQL** for future
  reporting/accounting requirements.

### Multi-tenancy requirements

- Tenant-owned tables must include an explicit `tenant_id`.
- **PostgreSQL RLS is evaluated as the database-level fail-closed enforcement
  mechanism**, rather than relying only on application query discipline.
- Repository/service boundaries must still **pass explicit tenant context**.
- Tenant isolation must have **integration tests proving cross-tenant reads and
  writes fail**.
- **Raw SQL must not provide an undocumented escape hatch** around tenant
  enforcement.

### Migration model

- **Module-owned schema definitions.**
- **One deterministic migration execution path** for each deployable
  application.
- **Generated migrations must be committed and reviewed**; production must
  never perform implicit schema synchronization.

## Alternatives considered

- **Prisma** — excellent DX and schema-first clarity, but **Prisma 8 is
  currently on its release-candidate line** (v8.0.0-rc.x, not yet GA as of
  2026-09-04). A foundational dependency should not be adopted on
  unreleased/transitioning functionality.
- **Kysely** — excellent typed query builder and SQL control, but it is a query
  builder only: schema definitions and migrations would require separate
  tooling, adding moving parts.
- **MikroORM** — capable entity-based ORM, but less SQL-transparent than the
  chosen approach.
- **TypeORM** — NestJS-native, but weakly typed query builder and maintenance
  velocity concerns make it a weaker fit for strict-mode + AI-enforced
  boundaries.

## Consequences

- Persistence code is SQL-transparent and fully type-inferred from module-owned
  schema definitions.
- Migrations are explicit, committed, reviewable SQL generated by Drizzle Kit.
- Tenant isolation can be enforced both in the repository/service layer (explicit
  `tenant_id` context) and at the database level (RLS), with integration tests
  proving the fail-closed behavior.
- Trade-off: Drizzle is lower-abstraction than Prisma, so conventions for
  tenant scoping, repository patterns, and migration ordering must be defined
  and enforced (docs + CI), rather than provided by a heavier framework.
